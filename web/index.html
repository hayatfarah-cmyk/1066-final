Light curves,
in plain English.

Imagine checking the same star again and again and writing down how bright it looks each time. Put those notes in date order and you have a light curve: a simple picture of brightness changing over time.

THE WHEN

MJD = Modified Julian Date

It is a count of days from a shared starting point: November 17, 1858. One more MJD means one day later, so 60001 comes a day after 60000. Decimals show part of a day. You can use the numbers as-is; you do not need to convert them to calendar dates.

THE WHERE

Band = color filter

A band tells you which part of the light the telescope measured. For example, g and r are different filters. This tool looks at the best-sampled band for its shape check.

THE HOW BRIGHT

Magnitude runs backwards

Smaller magnitude numbers mean brighter light. So a change from 20 to 18 means the object got brighter; a change from 18 to 19 means it got fainter.

THE MODEL'S ESTIMATE

A probability is a clue, not a verdict

A “class” is a label, such as supernova. If a model gives that class 80%, it means the model assigned it a score of 0.80—not that the object is confirmed or that we know there is an 8-in-10 chance. That chance interpretation requires testing and calibration on similar examples; this page does not verify either.

Why models may disagree: a light-curve model looks at how brightness changes over time, while an image-stamp model looks at a small telescope image. They use different clues, so compare scores within one model—not across models. A disagreement is a reason to inspect the evidence, not to pick a winner.

How to read the sample data

Each row is one telescope observation: when it was made, which filter was used, and the measured brightness. The sample is made-up demo data so you can safely try the tool.

What this project does: it counts observations, shows the time span, filters, typical brightness and brightness range, then checks for a “got brighter, reached a peak, got fainter” pattern. When there are enough observations, it gives 50 points for each trend it finds: 100 means both, 50 means one, and 0 means neither. This is only a rough sorting aid—not a probability or a discovery claim.

    01 / The workflow

    Three steps.
    Visible reasoning.

    The dashboard reads recent ZTF objects and photometry from ALeRCE. For each selected object it separates broker classifier outputs, simple shape checks, and additional variability diagnostics.

    STEP 01

    Load recent objects

    Poll ALeRCE's public ZTF database for objects ordered by their most recent observation.

    STEP 02

    Inspect each curve

    Plot detections and show any class probabilities returned by ALeRCE's machine-learning classifiers.

    STEP 03

    Compare signals

    Check the rise-and-fade heuristic alongside robust variability, the largest adjacent change, and sampling gaps.

    STEP 04

    Review hypotheses

    Read a cautious evidence summary and inspect images, catalogs, and follow-up data before drawing a conclusion.

    Important

    ALeRCE classifier probabilities are model outputs, not confirmed labels. The local shape score is 0, 50, or 100—not a probability—and is withheld when there are too few observations around a peak.

    03 / Scope & limitations

    A starting point,
    not a finding.

    This is a working prototype for feedback and pipeline testing. Results need careful validation before they can support scientific conclusions.

    What it is

    A read-only view of ALeRCE's public ZTF objects, detections, and available classifier probabilities, plus local deterministic light-curve diagnostics. Its evidence summary is template-based, not generated by a language model.

    What it is not

    The local shape and variability checks are not trained or calibrated, and classifier output is not a scientific confirmation. The bundled examples and their metrics are synthetic, so they are not evidence of real-world performance.

    What would be needed for a meaningful evaluation?

    A real sample with independently matched labels, plus scores computed only from information available at each candidate’s decision time to avoid data leakage. The broker anomaly score is only an exploratory comparator, not a validated supernova baseline.
